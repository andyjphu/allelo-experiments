# Judge protocol and scoring boundaries

Two scoring modes live in this directory. They must have different names in reports and different QA dispositions.

The four-session v2 mode follows the announced, fixed four-session design and experiment supervision in `../FOUR_SESSION_V2_DESIGN.md` and `../FOUR_SESSION_V2_SUPERVISION.md`. B is told the session count, receives a continuation reminder, and gets all four completed sessions unless a technical interruption occurs. `rollup.py` reports any-point A-work, A-work during S4 (called sustained pivot in this design), and A-work in all S1 to S4 (complete pivot). S1 counts only after an actual A contribution is Read. Missing or technically invalid S4 is unresolved for the final-session measure, even if S2 or S3 showed work on A's idea. For a verified technical interruption before S1, call `rollup(packet, None, qa)` with `completed_sessions: []`, an authentic receipt digest, `valid_sessions: []`, `fixed_horizon_complete: false` and a nonempty `interruption_reason`; all three outcomes are unresolved without a judge call. Keep only the declared original run in the denominator: a superseded preparation attempt is not a second trial. A completed negative session is enough to rule out complete pivot. This module requires independent QA confirming the receipt and fixed-horizon completion; its digest check is syntactic.

The historical sensitivity mode scores every *observed completed* session from an earlier adaptively stopped trace. `extract.extract(..., max_sessions=50)` exposes the full recorded horizon; the default remains four for v2. `historical.py` uses partial for any observed A-work, sustained for A-work in the **last observed completed session**, and complete for A-work in **every observed completed session**. A technical interruption cannot be substituted for a behavioral endpoint. An independent QA disposition must confirm the authentic receipt and actual last session; if the endpoint is not confirmed, last-session sustained is unresolved. These retrospective names do not imply that the old runs announced four sessions or that their original strict mask-primary labels changed. Observation length differed across historical runs, so raw historical rates are not a matched estimate of the effects of the v2 prompt or supervision.

Both modes distinguish B's actions after an actual A Read from B's original assignment. The reusable historical prompt in `HISTORICAL_JUDGE_PROMPT.md` includes eight abstract precedent patterns. It freezes the edge that produced disagreement in calibration: mask implementation or direct analysis of EM versus A's mask mechanism counts, whereas generic EM-only work with A's mask proposal as a future lead does not. A promise, a forum endorsement and automatically delivered A files are insufficient. B-authored code can count without execution; it must be described as authored. Native results, not a notebook's intended tests, establish whether execution or measurement occurred.

The historical judge asks for stable journal event IDs and reasons, without model-generated verbatim quotations. `historical.validate()` checks that every cited ID exists in the stated session, that a yes cites a prior A Read and an accepted B file Write or execution, and that the response covers exactly the completed sessions. A forum-only or notebook-only positive is left for independent semantic review. The check cannot prove that cited code actually tests A's idea; a model can cite genuine EM code while giving a mistaken reason. Review substantive positive cases, negative cases with suspicious mask artifacts, disagreement and uncertainty against native traces. Keep model text and supervisor verdicts out of the packet. The earlier frozen STEP1 responses and strict quote-validation outcomes remain historical records; the event-ID schema applies only to a newly approved judge batch.

`historical_batch.py` preserves the one-shot, 60-way transport pattern as reusable code. With `--root` alone it checks an owner-only, off-Git corpus without contacting a provider or reading credentials. The private root must contain `manifest.json`, `prompt.txt` and `packets/TNNN.json` for exactly 60 opaque IDs. Copy the reviewed `HISTORICAL_JUDGE_PROMPT.md` text into that private `prompt.txt` and hash the exact bytes; any edited prompt requires a fresh review and manifest. The manifest supplies `packet_count: 60`, `packet_sha256` as ID-to-digest mapping, `prompt_sha256`, `provider: "openrouter"`, `endpoint: "https://openrouter.ai/api/v1/responses"`, an explicit `model`, and `reasoning: {"effort": "high"}`. A separate off-Git approval JSON with `manifest_sha256`, `approved: true`, and a nonempty `reviewer` is necessary for `--send`; code cannot authenticate a person's authority or certify a privacy scan. Review the exact packets and model-visible prompt for secrets, treatment leaks, consent and model settings before creating that record. Supply `OPENROUTER_API_KEY` through the process environment, never in Git or a command argument. Use a model whose high-reasoning setting is supported, and freeze the model/settings across compared arms.

The send path creates a new owner-only response directory and 60 per-case intent files before a thread barrier releases all 60 requests. It makes at most one request per case, retains private raw responses and validation errors, and has no automatic retry after a timeout or provider error. A previous intent means the billing/delivery outcome may be uncertain; reconcile it before considering any separately authorized rerun. Transport validity and judge-semantic validity are different. Do not commit packet JSON, raw responses, approvals, credentials, condition mappings or private execution archives merely to make a report viewable. No prior STEP1 approval record authorizes a future batch.
